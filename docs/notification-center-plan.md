# 博客通知（Base UI Toast）

2026-10-22。站长和访客在博客里共用右下角临时提示。采用 Base UI 1.9.0 官网 Toast 示例的样式、堆叠和过渡，不做带历史记录的通知中心。

## 这几个词是什么意思

- 管理员入口：站长查看投递成功或失败记录的地方。继续使用现有后台的 Webhooks 页面，博客不增加站长登录入口。
- 跨设备已读：电脑看过某条消息后，手机也知道它已读。这轮不做已读标记，不需要账号同步。
- 保留历史：弹窗消失后仍能打开列表翻旧消息。这轮不保留，刷新或离开期间的消息也不会补发。

## 哪些提示给谁看

| 事件 | 接收范围 | 标题 | 内容 |
| --- | --- | --- | --- |
| 新的公开文章 | 当前在线访客和站长 | 有新文章了 | 博客发布了新文章，可以前往文章列表看看。 |
| 文章修改 | 正在阅读对应文章的人 | 文章有更新 | 你正在阅读的文章已修改，稍后刷新可查看最新内容。 |
| 文章删除 | 正在阅读对应文章的人 | 这篇文章已移除 | 当前文章已删除，可以返回文章列表继续阅读。 |

沿用 Core 的访客 `/web` 实时连接。进入详情订阅 `article-文章ID`，离开退出，断线重连后重新订阅。新文章只有 `isPublished === true` 才显示通知。仅展示固定文案，不把事件中的全文、管理错误或敏感字段放入提示。

“所有人都能看到通知”不表示“所有后台消息都公开”。健康检查、签名失败、缓存失效结果仍在后台投递记录查看。评论、手记等尚未接入的新功能不提前弹通知。

Webhook 仍负责使 Next 缓存失效；Socket.IO 负责把内容变化消息送到当前浏览器，两者独立。收到弹窗不能证明缓存已完成失效，因此不会显示“缓存刷新成功”，也不自动刷新或跳转打断阅读。若立即刷新仍是旧内容，检查 Webhook 投递状态。

## 自己在哪里修改

编辑 `apps/web/lib/notification-copy.ts`：

```ts
export const notificationSettings = { timeout: 5000, limit: 3, close: "关闭" };
```

- `timeout` 是自动关闭时间，单位毫秒，5000 就是 5 秒；0 表示不自动关闭。
- `limit` 是同时展示数量，默认 3；超过后由 Base UI 收起较旧提示。
- `close` 是关闭按钮文字。
- `notificationCopy.POST_CREATE / POST_UPDATE / POST_DELETE` 中的 `title` 和 `description` 分别是标题与正文。修改后开发服务会热更新。

例如将 `POST_CREATE.title` 改为“我又写了一篇”，只改变新文章提示的文字，不影响订阅事件和缓存。

`apps/web/app/notifications.tsx` 负责连接和 Toast 结构。`apps/web/app/notifications.css` 来自[官网示例](https://base-ui.com/react/components/toast)，只改为项目前缀类名，并补减少动态效果与长文本换行。位置在 `.notification-viewport`，桌面右下边距 2rem、宽度 22.5rem，手机边距 1rem。要改间距就在这里改；堆叠变量和动画先保留官方实现。

浏览器连接地址由服务端布局基于现有 `MIX_SPACE_API_URL` 的 origin 加 `/web` 得到，本地即 `http://127.0.0.1:2333/web`。当前要求 Core 同一 origin 暴露默认 `/socket.io` 通道；将来部署到内部域名或子路径时需独立配置公开网关地址。

## 验证边界

`node scripts/verify-notifications.mjs` 检查公开文章筛选、通知文案映射和内部事件排除。浏览器使用模拟 Socket.IO 消息验证实际 Base UI 组件，不写日常文章；不能将它称为本轮真实发布端到端验收。已有 Webhook 的真实隔离库联调记录仍见 [Webhook 文档](./webhook-local.md)。

本轮类型检查、ESLint、轻量回归通过。实际浏览器通过桌面右下定位、堆叠、悬停暂停计时、关闭、自动消失、手机宽度、进入详情订阅和离开退出检查；本地 Core 的真实 Socket.IO 握手也通过。UI事件使用协议替身，未在日常库发测试文章。新增依赖后的旧开发进程反复热更新，重启同一套服务后验证通过；没有改热更新配置。测试浏览器已关闭，日常服务保留运行。
