# 统一通知栏方案（未实施）

用户希望接收到通知后有统一入口。本轮只做考虑，不新增通知栏、登录流程、WebSocket 或 SSE。

## 先区分两类通知

| 类型 | 默认可见对象 | 内容 |
| --- | --- | --- |
| 管理通知 | 已认证的站长 | 健康检查、Webhook接收/校验结果、缓存失效成功或失败 |
| 博客更新提示 | 访客，需另行确认 | 有新的公开内容，可以刷新；不包含草稿、隐藏文章、删除正文或内部错误 |

Webhook 是服务器之间的请求，本身不会把消息发送到浏览器。缓存失效、通知栏出现消息、页面实际刷新是三个步骤，不能用同一个“成功”混在一起。

## 建议最小实现

1. 在既有右栏或顶部放统一通知入口，展开后展示简短记录；失败/需要操作的状态再给一次轻提示。
2. 管理通知优先复用 Core 已有的 `webhook_events` 投递记录，不再创建重复存储。查询必须走管理员鉴权，不能把原始 payload、签名头或密钥返回公开页面。
3. 每条显示事件名称、时间、文章标识和状态。HTTP200且 `revalidated: true` 才标“缓存已失效”；`health_check` 标“连通检查通过”。发送中/失败需分别显示。
4. 首版可在展开通知栏时获取最新记录，提供刷新。是否需要持续推送，再比较后台已有连接、低频轮询与 SSE，不先引入新服务。
5. 使用投递记录ID作为列表身份。自动重试与手动重发不混作新文章发布；后续若需要业务事件去重，应扩展明确的事件ID，不能假定当前 `X-Webhook-Id` 是投递ID（它是 webhook 配置ID）。

## 需要后续确定

- 通知栏只给站长，还是也要给访客展示公开更新提示？默认建议先做站长管理通知。
- 管理员入口放在后台还是新前端？新前端目前没有站长登录，不能为了显示通知直接公开管理接口。
- 已读状态是否跨设备同步？是否保留历史？这些决定后再增加持久化，不预建通用消息系统。

验收应包含权限隔离、错误与成功状态、重发不刷屏、键盘操作与手机显示。此方案不改变本轮已经接通的服务端缓存失效逻辑。
