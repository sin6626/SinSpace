# 本地 Webhook 与后台测试

本轮只接本地环境，不改线上。接收端为 `apps/web/app/api/webhooks/mix-space/route.ts`，仅接受签名有效的文章创建、修改、删除，以及健康检查。

## 启动

```sh
pnpm dev
# 在另一个终端，仅在需要后台时运行
pnpm dev:admin
```

也可在全部服务已停止时使用 `pnpm dev:all` 同时启动。不要再叠加旧项目的同端口服务。

- 新前端：`http://127.0.0.1:2323`
- 本地 Core：`http://127.0.0.1:2333`
- 本地后台：`http://127.0.0.1:9528`

后台源码已放到 `apps/admin`，原编辑器暂时保留，Plate 迁移仍按独立计划推进。

## 后台如何配置

本机根 `.env.local` 已生成 `MIX_SPACE_WEBHOOK_SECRET`，没有输出到聊天或提交 Git。打开这个本地文件，将它的值复制到后台 Secret 字段；修改后需退出并重新运行根命令 `pnpm dev` 或 `pnpm dev:web`，仅刷新浏览器或重启 Next worker 不会重新读取启动器环境。

进入后台“附加功能 → Webhooks”（`/extra-features/webhooks`），创建一条：

| 字段 | 填写值 |
| --- | --- |
| Payload URL | `http://127.0.0.1:2323/api/webhooks/mix-space` |
| Secret | 根 `.env.local` 中 `MIX_SPACE_WEBHOOK_SECRET` 的值 |
| 触发事件 | `POST_CREATE`、`POST_UPDATE`、`POST_DELETE` |
| 触发范围 | 勾选“访客”和“系统”，合计 5 |
| 启用状态 | 开启 |

**日常库的这条配置需要你按表创建。** 隔离测试配置已清理，不会把测试账号或测试密钥混入日常库。建议只登记一条匹配地址的配置，避免重复推送。

保存时 Core 会发送 `health_check`。也可以点击“发送健康检查”，然后在投递记录查看 HTTP 状态和 Response：

- 健康检查成功：HTTP 200，`revalidated: false`。只证明地址与签名能接通，没有清理文章缓存。
- 文章事件成功：HTTP 200，`revalidated: true`。后续服务端读取会重新获取文章，不代表已打开的访客页面主动刷新。
- 已发送不等于投递成功，以记录中的状态和响应为准。失败记录可点击“重新发送”。

旧后台的测试地址与 Core 不一致，本轮已改为使用现成的 `PATCH /webhooks/:id` 健康检查，并将重发地址修正为 `POST /webhooks/redispatch/:eventId`。因此测试按钮只做健康检查，真实文章事件通过实际发布/修改/删除测试文章验证。

## 接收与缓存规则

- 使用 `X-Webhook-Signature256`，对原始请求体做 HMAC-SHA256 与恒定时间比较。
- 请求体限制 4MiB；无配置返回503，签名错误401，格式/事件错误400，超限413，缓存操作失败500。
- 三种文章事件均使 `blog:posts` 和 `blog:categories` 立即过期，覆盖列表、详情、旧slug缓存及分类信息。不会按请求提供任意缓存标签。
- 不记录密钥或文章正文，不展示通知 UI，不修改文章。
- Core 的签名不覆盖事件/时间戳请求头，本轮不声称提供防重放。重复通知只重复执行幂等失效。Core 的更新事件有约1秒防抖，通知本身异步。

## 验证

`pnpm verify` 是轻量检查，不启动真实服务。

`pnpm verify:webhook:local` 必须在日常服务停止后执行。它先编译 SDK/Core，再使用 `.local/verification` 隔离库、独立端口与专用测试账号。为控制资源，测试运行已编译的 Core，不同时启动 Nest 编译监听；普通开发命令不变。仅删除本脚本创建的测试文章和带验证标记的 webhook，不操作日常库。所有凭据仅保存在忽略的本地文件中。

本轮真实验证通过：签名健康检查、发布后刷新已缓存列表、修改后刷新列表和详情、删除后列表移除且旧详情不再显示、错误签名401、健康检查按钮对应API、真实重发。早期测试发现 runtime 声明不兼容 Cache Components、测试初始化判断与 DELETE 请求头问题，均已修正并保留失败记录。一次完整监听栈超过2560MiB预算后已清理，改为预编译Core后通过；没有提高预算。

后台静态类型、健康检查/重发调用绑定以及两个既有编辑器模型检查通过。实际浏览器冷启动两次触发资源保护，均已清理，未完成登录与表单验收。日志暴露的 Vite 8 JSX 依赖扫描配置已修正，后续启动日志未再出现该解析错误；不能据此宣称后台完整可用。
